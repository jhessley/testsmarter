Test Smarter Outbound Agent Integration Outline

Purpose

This document describes the integration flow between the Test Smarter platform and the Retell outbound agent. The platform owns order selection, patient/order data lookup, call scheduling, and post-call updates. Retell owns the phone conversation and returns the outcome needed to schedule the next action.

Core rule: initiate an outbound call when an order is in one of the eligible buckets, that bucket's follow-up date is either blank or less than or equal to today's date, and the order's human_follow_up_required value is false.

The backend is responsible for selecting the correct bucket-specific follow-up date, note, and human follow-up namespace. This page uses normalized names to describe the flow.

Eligible Buckets

Bucket Test Type Likely Agent Context Primary Goal
HST patient scheduling HST Patient needs to finish paperwork and/or satisfy the copay/card step before the home sleep test can move forward. Guide the patient based on the current paperwork and payment state, or route them to a human if scheduling needs manual help.
HST patient testing HST Device has been delivered but the home sleep test has not been completed or returned. Encourage the patient to start/complete testing and return the device.
HST pending return HST Test is complete, but the device has not been returned. Get the patient to return the device using the included packaging.
POX delivered POX Pulse oximetry device has been delivered but testing/return is still outstanding. Encourage the patient to complete the overnight oxygen test and return the device.
POX pending return POX Pulse oximetry test is complete, but the device has not been returned. Get the patient to return the device.

Call Eligibility

Selection Criteria

  1. Order bucket is one of the five supported outbound buckets.
  2. The bucket-specific follow-up date is blank, or the bucket-specific follow-up date is less than or equal to the platform's current local date.
  3. The order's human_follow_up_required value is false.
  4. Patient has a callable phone number.
  5. Order has not moved to a terminal state that should suppress outreach, such as device returned, report generated, or order completed.

High-Level Flow

Find Eligible Orders

On the scheduled outbound job, query orders in the supported buckets whose bucket-specific follow-up date is due or blank and whose bucket-specific human follow-up flag is false. Throttle and schedule call creation so potential office transfers do not overload staff.

Build Retell Dynamic Variables

For each order, gather patient, provider, order, device, testing-condition, shipment, return, late-fee, and prior follow-up context. Send these values as Retell dynamic variables.

Create the Outbound Call

Use Retell's phone-call creation endpoint from a backend service.

Agent Completes Conversation

The agent completes the call or leaves a voicemail.

Write Back Outcome

At call conclusion, update the platform with the new follow-up date, follow-up note, and whether the next follow-up must be handled by a human.

Data Sent To Retell

Known fields below come from the existing test harness and initialization logic. Exact source columns may need to be mapped to the platform schema.

Important: all dynamic variable values must be converted to strings before sending to Retell. Booleans, timestamps, numbers, arrays, and objects should be serialized as strings in retell_llm_dynamic_variables.

Dynamic Variable Description Use
patient_first_name, first_name Patient first name. Patient verification and conversational personalization.
patient_last_name, last_name Patient last name. Used to form formal_patient_name.
patient_sex, patient_gender Patient sex/gender value when available. Used to select "Miss" or "Mister" in the formal greeting.
provider_name Ordering provider or office name. Used in the reason for call and voicemail message.
order_id Platform order identifier. Allows the agent/integration to reference the correct order in logs, tools, and writeback.
order_test_type Expected values include HST and POX. Determines home sleep test vs overnight oxygen test language.
device_type Device model/type assigned to the order. The agent derives device instructions from order_test_type and device_type.
number_of_nights Number of nights the patient should test, converted to a string. Helps the agent explain how long the patient should use the device.
nightly_testing_conditions JSON string representing an array of objects, one object per night of testing. Each object contains instructions for supplemental oxygen and/or PAP device use. Lets the agent answer testing-condition questions and guide the patient through each required night.
order_bucket Current platform bucket/status. Determines whether the order needs scheduling, testing, or return follow-up.
hst_paperwork_finished_at Mapped from order.hst.paperwork.meta.finishedAt. For HST patient scheduling, tells the agent whether paperwork/questionnaire is complete.
copay_paid_at Mapped from order.copayPaidAt. Strongest signal that the copay was fully paid.
hst_payment_bypassed Mapped from order.hst.paymentBypassed. When true, payment can be treated as satisfied without collecting payment.
hst_payment_status Mapped from order.hst.paymentSession.payment_status. no_payment_required means card information is saved and payment requirement is satisfied without a copay charge.
hst_payment_invalidated Mapped from order.hst.paymentInvalidated. When true, prior payment should not be treated as cleanly satisfied for next-step automation.
order_shipped_at, shipment_delivered_at Shipment and delivery timestamps, converted to strings. Used to calculate days in possession and call urgency.
order_is_shipped_back, order_shipped_back_at Whether the device is already on its way back. Boolean and timestamp values must be converted to strings. Suppresses normal testing/return urgency when true.
order_device_returned_at Timestamp when the device was received back, converted to a string. Indicates no further return reminder is needed.
order_completed_at, order_report_generated_at Completion/report status timestamps, converted to strings. Indicates the order may be complete and should not receive a normal reminder.
late_fee_waived Stringified boolean. Stub to false for now. Prevents late-fee language when waived. Automatic late-fee application is planned for the platform, and users will be able to waive late fees on a per-order basis.
follow_up_notes Existing follow-up notes from previous outreach. Gives the agent prior context before the next call.

HST Scheduling Payment And Paperwork States

For the HST patient scheduling bucket, the agent needs these state signals so it can guide the patient to the correct next step.

State Signals Operational Meaning
Paperwork incomplete, payment incomplete hst_paperwork_finished_at empty, copay_paid_at empty, hst_payment_bypassed false/empty, hst_payment_status is not no_payment_required. Still waiting on paperwork and payment/card step.
Paperwork complete, payment incomplete hst_paperwork_finished_at set, copay_paid_at empty, hst_payment_bypassed false/empty, hst_payment_status is not no_payment_required. Questionnaire is done, but payment still needs attention.
Paperwork complete, copay paid hst_paperwork_finished_at set and copay_paid_at set. Strongest fully paid signal.
Paperwork complete, card saved but no payment collected hst_paperwork_finished_at set, copay_paid_at empty, and hst_payment_status is no_payment_required. Payment requirement is satisfied without an actual copay charge. In the UI this shows as "Card information saved."
Paperwork complete, payment bypassed hst_paperwork_finished_at set and hst_payment_bypassed true. Move forward without collecting payment.
Payment previously done but later invalidated hst_payment_invalidated true. Do not treat prior payment as cleanly satisfied for next-step automation.

Post-Call Writeback

At the conclusion of every call attempt, the agent/integration should update the source order with the next follow-up state. Each bucket has its own follow-up date/note namespace, and the backend should write to the namespace for the bucket that triggered the call.

Field Type Purpose
follow_up_date Date or blank/null Controls when the order becomes eligible for the next outbound attempt.
follow_up_note Text Human-readable summary of what happened and what should happen next.
human_follow_up_required Boolean Marks whether the next follow-up should be handled by a person instead of the outbound agent.
human_follow_up_reason Text or enum plus optional detail Stores why human_follow_up_required was set to true. Leave blank when human follow-up is false.

Writeback source precedence: the post-call webhook should write values from the call object's collected_dynamic_variables first. These values are set in real time by the agent during the call using the full prompt and conversation context.

  1. Preferred: use collected_dynamic_variables.follow_up_date, collected_dynamic_variables.follow_up_note, collected_dynamic_variables.human_follow_up_required, and collected_dynamic_variables.human_follow_up_reason when present.
  2. Fallback: if collected values are missing, use analyzed values from the call object, such as analyzed_follow_up_date, analyzed_follow_up_note, analyzed_human_follow_up_required, and analyzed_human_follow_up_reason.
  3. Default: if neither collected nor analyzed values are present, set follow-up date to today plus 3 days, follow-up note to a fallback explanation, human_follow_up_required to false, and human_follow_up_reason to blank.

Recommended Outcome Rules

Call Result Follow-Up Date Human Follow-Up Human Reason Note Guidance
Patient agrees to complete test or return device Set to next retry date. false Blank. Summarize patient commitment and expected action.
Patient needs help, has clinical/order questions, or requests office Soonest possible date. true Use a concise reason such as help needed, clinical question, order question, or requested office. Capture the requested help and any transfer attempt.
Voicemail left Set to next retry date. false Blank. Record that voicemail was left and include the general message category.
Bad phone number, opt-out, escalation, complaint, or unsafe automation case Soonest possible date. true Use the specific blocker, such as bad number, opt-out, escalation, complaint, or unsafe automation case. Capture the reason clearly for the human queue.

Transfer follow-up: when the call is transferred to the office, the post-call writeback should set human_follow_up_required to true with the earliest possible follow-up date in case the transfer fails. When staff takes the call, they should set the next follow-up date and decide whether the order still requires human follow-up.

Platform And UI Changes Needed

  • Add human follow-up fields to the platform data model: human_follow_up_required and human_follow_up_reason.
  • In the UI where users enter the follow-up date and note, add controls for the human follow-up required fields.
  • When human_follow_up_required is true, require or strongly prompt for human_follow_up_reason so the human queue has clear context.
  • In the bucket order lists, make human-required orders visually distinct by either coloring the follow-up date differently or adding a dedicated human follow-up indicator column.
  • Make bucket order lists sortable and filterable by human follow-up required so users can quickly find orders that need their attention.
  • Ensure the backend selection logic excludes orders where human_follow_up_required is true from automated Retell agent calls.
